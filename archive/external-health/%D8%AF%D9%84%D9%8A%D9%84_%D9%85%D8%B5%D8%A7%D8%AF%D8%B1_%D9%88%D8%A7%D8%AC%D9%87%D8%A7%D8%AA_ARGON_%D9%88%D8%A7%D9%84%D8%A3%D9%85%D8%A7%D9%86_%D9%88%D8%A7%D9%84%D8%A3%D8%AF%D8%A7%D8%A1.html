دليل المصادر العالمية لبناء واجهات طبية قوية وآمنة

كتالوج عملي يجمع أنظمة طبية حقيقية، ومستودعات كود، وأنظمة تصميم ومكونات، ومعايير للأمان والأداء وإمكانية الوصول والتكامل. الهدف: بناء واجهة ARGON أكثر وضوحًا وسرعة وديمومة، من دون نسخ تصميم محمي أو إدخال مكتبات غير مفحوصة إلى نظام صحي.

46 مصدرًا مختارًامراجع طبية + كود مفتوحإمكانية الوصول والأمانالعربية وRTLتمت المراجعة: 10 أكتوبر 2026
قاعدة الثقة: وجود مستودع مشهور أو رخصة مفتوحة لا يثبت أنه آمن أو مناسب طبيًا. قبل الاعتماد افحص الرخصة الفعلية، ونشاط الصيانة والإصدارات، وسياسة الأمان، والاعتماديات والثغرات، والاختبارات، وأثر المكوّن على بيانات المرضى. استخدم صور الأنظمة التجارية كمراجع داخلية لا كأصول لإعادة النشر.

الخلاصة التنفيذية — ما الذي أوصي به لـ ARGON؟

1. مرجع لسير العمل الطبي

ابدأ بـ OpenMRS O3 وBahmni وMedplum. افتح نسخة العرض أو معرض الصور، ثم وثّق كل رحلة مستخدم: المدخلات، الحالات، الأخطاء، الصلاحيات، والنتيجة. لا تقلّد الألوان وحدها.

2. أساس واجهة قابل للتطوير

اختر نظامًا واحدًا: shadcn/ui + Radix لهوية مخصصة، أو Carbon / Fluent UI / MUI إذا كانت الجداول والمكونات الجاهزة أولوية. لا تجمع عدة أنظمة رئيسية عشوائيًا.

3. الواجهات الطبية الكثيفة

TanStack Table + Virtual لقوائم المواعيد والنتائج، React Hook Form + Zod للنماذج، TanStack Query لجلب البيانات، وECharts للرسوم التشغيلية. تُراجع صلاحيات وتخزين بيانات كل مكون قبل الإنتاج.

4. الجودة كجزء من التصميم

Storybook لكل مكوّن، Playwright للرحلات وصور المقارنة، axe-core وWCAG 2.2 للإتاحة، وLighthouse CI/Core Web Vitals للأداء. لا تكتفِ بصورة جميلة أو بنتيجة فحص آلي واحدة.

كل شاشة لديها حالات كاملةLoading، Empty، Error، No permission، Stale data، Unavailable integration، Read-only، Unsaved changes، Saved/Failed. لا تُخفِ فشل الحفظ.
تدفق العمل قبل الزخرفةقلّل التنقل غير الضروري، لكن لا تضع بيانات طبية خطرة في مكان غير واضح ولا تخفِ مصدر المعلومة أو تاريخها أو حالة اعتمادها.
العربية وRTL جزء من التصميماختبر ترتيب العناصر، اتجاه النصوص المختلطة، الأرقام والمعرّفات والجرعات والتواريخ، الخطوط، لوحة المفاتيح، والتقارير المطبوعة باللغتين.
لا بيانات مرضى حقيقية في صور التصميم أو سجلات التتبعاستخدم Synthea أو بيانات اصطناعية. امنع تسريب PHI في console logs وanalytics وsession replay، وراجع التخزين المؤقت وعمر الجلسة.
اعتماد المكتبة بعد فحصها فقطالمالك والنشاط والإصدارات والرخصة والإعتماديات والثغرات وسياسة الأمان والاختبارات كلها مطلوبة قبل إضافتها إلى منتج صحي.

خطة تطبيق عملية على ARGON

المرحلة A — المرجع البصري

اختيار 8–12 رحلة عمل مهمة وتسجيل صور المصادر، وما يعجبك في كل شاشة، وما يسبب بطئًا أو غموضًا. لا تخلط لقطة شاشة مع دليل أن الميزة تعمل.

المرحلة B — Design System

تحديد tokens للألوان والمسافات والطباعه والحالات، ثم بناء App Shell والتنقل والنماذج والجداول والتنبيهات وحالات التحميل والخطأ في Storybook.

المرحلة C — اختبار التصميم

اختبار RTL/LTR، keyboard، قارئات الشاشة، تصغير الشاشة، zoom، أداء فتح ملف المريض، وجولات استخدام مع موظفي استقبال وأطباء ومختبر وصيدلة.

المرحلة D — حماية الاستدامة

فحص اعتماديات ورخص في كل PR، صور Playwright مقارنة، قياس Core Web Vitals، تحديثات آمنة، سياسة deprecation للمكونات، وسجل قرارات التصميم.

قائمة فحص قبل اعتماد أي مستودع

  • الرخصة موجودة وواضحة في الجذر ولكل حزمة/أصل خارجي؛ فحص الرخصة لا يستبدل المشورة القانونية.
  • المشروع غير مؤرشف، وله إصدارات حديثة ونشاط صيانة وسياسة أمان وآلية للإبلاغ عن الثغرات.
  • الاختبارات وCI تعمل في إصدار محدد؛ اقرأ القضايا المفتوحة وسجل التغييرات وملفات الأمان.
  • فحص الثغرات والاعتماديات والرخص وSBOM؛ ثبّت نسخًا دقيقة وافحص تحديثات السلسلة.
  • اختبر ملاءمة RTL والعربية والوصول بلوحة المفاتيح وقارئات الشاشة مع بيانات اصطناعية.
  • راجع حجم الحزمة وأداء الإنتاج وتوافق المتصفحات ودعم لوحة المفاتيح وحالات الفشل.
  • لا تستخدم بيانات ديمو عامة لإدخال معلومات مرضى حقيقية ولا تضع أسرارًا أو PHI في screenshots.
